# Pill happens

A quiet medication journal for personal use. Open a password's private journal, log an intake, and see the current tracking day at a glance.

Built with **Next.js 16.4.3**, **React 19.3.1**, TypeScript, Tailwind CSS 4, and shadcn/ui components using Base UI. The production app is designed to run on Vercel and store its journal in Neon Postgres connected through the Vercel Marketplace.

## The experience

- **Password journals:** enter an existing password to open its journal. A password without a journal opens a confirmation drawer on mobile or dialog on desktop. The exact password appears in a highlighted panel; **Create journal** creates an empty, separate journal and signs in. Going back creates nothing and keeps the entered password available to correct. Anyone using the same exact password opens the same journal.
- **Today:** a compact date and live 24-hour clock, styled to match the consecutive logging-day count and “/ in a row” detail opposite it. A playful filled heart-calendar and muted dot lead the date, matching the permanent stars icon and dot beside the streak count. Both markers share one rendering component, with identical 22px sizing, inherited primary color, filled weight, and 4px gaps. On the narrowest phones, 16px heading gutters and a 4px minimum gap between the two halves keep the complete labels visible. The slightly larger primary labels, muted contexts, and icons align on one centered horizontal row, including narrow phones. The clock follows the journal timezone, updates each minute, and uses `00:00` at midnight. A clear 37px gap separates the row from the entries, without a divider. Intake entries follow directly below in chronological Date & Time Taken order, from earliest to latest. The entries area expands to fill the available screen height, with a “Logged X Today · so far” summary and an icon-free “New day at 06:00” hint just above the logging button. The summary matches the date row's typography, adds a filled confetti icon and a larger context dot, and keeps the reset hint as concise text. Historical day summaries use “that day” rather than “Today”. The “Log an Intake” button uses a playful bold capsule-and-spark mark in a 28px box (26px on narrow phones). Its leading mark, label, slash, live count, and trailing arrow form one intrinsic, centered, nonwrapping group without an expanding caption or edge-pinned arrow. A stronger 4px automatic specular rim follows its existing 22px corners while the 64px size, theme fill, text sizes, and caption opacity retain their established styling. Light mode uses a charcoal fill with peach content; dark mode keeps its peach fill and ink content. Both the button caption and the summary row use explicit line-height alignment, with compact padding and gaps on narrow phones. This action area stays fixed near the bottom on mobile, with safe-area spacing and room for the last entry to scroll clear. A gradual fade starts 120px above the dock: neutral porcelain in light mode, ink at a maximum 40% opacity in dark mode, independently of the fully visible controls; on larger screens it sits at the bottom of short pages and follows longer lists. Content can grow and scroll normally when it needs more than one screen.
- **Pull To Refresh:** drag the branding pill down at least 96px and release when the progress badge says **Release To Refresh**. The handle moves with gentle resistance inside the header's existing spacing. A normal tap still goes home; **Refresh Page** in the navigation provides the same action without dragging. Only a gesture beginning on the brand is captured, leaving normal page scrolling unchanged. Short, upward, horizontal, multi-touch, cancelled, and lost-focus gestures never refresh; dragging back cancels, and the drag's follow-up click cannot navigate home. Refresh is disabled while a save is pending. A theme-aware glass loading screen appears before a full document reload of the current URL, rather than a client-only router refresh. A timestamp-and-route-only session-storage marker keeps this state visible after navigation until the journal loads or exposes its existing retry error. The marker expires after one minute; a 23-second cover limit prevents an endless overlay, and blocked storage still allows the full reload with the normal journal loading state. Underlying controls are inert during the cover. Reloading does not change the persistent sign-in cookie or activate a waiting service-worker update; the existing app-update action stays separate. Loading motion respects reduced-motion preferences.
- **Logging:** a shadcn bottom drawer on mobile and a centered dialog at widths of 768px and above. Choose a medication, select or enter a quantity, check the calculated dose, set the time taken, and optionally add a note.
- **Evening Check-Ins:** a compact frosted button appears below the intake list at **20:30 in the journal timezone**. It opens the shared mobile drawer or desktop dialog for a short reflection, up to four moods, optional energy and stress ratings, sleep hours, and one thing that helped. Every field is optional, but saving requires at least one response; no ratings are filled in for you. After saving, a more filled summary appears above the day's intakes with selected values and an edit action. The evening remains attached to the same tracking day after midnight until 06:00. Past-day logs allow missed check-ins at any hour, while future days cannot be saved. Each journal stores one editable check-in per day; updating it preserves its original creation time. An open draft keeps the day it was opened for, including across the 06:00 rollover. Reflection-only days appear in History, and backups include check-ins. They never count as medication intakes or extend the intake logging streak.
- **Guide:** a single quiet **Guide** link sits below the main intake button, with tiny secondary text and a larger invisible touch/focus target. It opens `/guide` inside the signed-in journal. Nine sections combine getting-started steps, feature reference, expandable answers, installation and backup help, and copyable colors in the existing warm system-theme design. The color reference covers 42 theme roles and all 312 medication accents, with visible usage notes, name/hex search, family filtering, individual and bulk copy, and a manual-selection fallback when clipboard access is unavailable. Copying colors never changes the app theme or a medication. The mobile dock reserves extra space for the link so the final intake or check-in can still scroll fully into view.
- **Medications:** create and edit the name, optional active ingredient (Wirkstoff), strength, medication type, color, icon, and icon angle. The optional ingredient input sits directly below the name; unknown ingredients can stay blank and saved ingredients can be cleared later. A compact Benzo switch sits beside that input in roughly 28% of the row. It stores a manual benzodiazepine flag; existing medications start unmarked, and neither names nor ingredients trigger automatic classification. A default intake quantity sits beside the per-unit strength, including tablets, capsules, drops, metered pumps, or other units. New logs prefill the selected medication’s default; older medications start at one unit. Editing an existing intake keeps its recorded quantity, including when changing the medication. Medication name, strength, and type edits apply to every linked past log; changing strength also recalculates historical doses and totals. The full-width appearance studio combines 312 compact color swatches with one search for 1,703 Lucide drawings, 45 checked-in SVG icons, and 343 curated emoji. The local SVG library includes 16 Lucide-compatible medication outlines and 17 flat-color illustrations, including the Tadalafil 5mg/10mg tablets, Tramal/Testavan dispensers, and the quarter-scored Levomethasan tablet. Search in English or German, or paste a single emoji. A large live showcase includes the actual journal-row appearance, a “Surprise me” action, and Undo. Medication type uses a compact full-width menu styled like the navigation, with a small option-count header, 16px leading icons, and a highlighted choice with a checkmark and “selected” label. Native keyboard navigation, typeahead, and focus restoration remain available. Other medication selection choices also include a leading icon. Archive a medication to remove it from new-log choices; restore it whenever needed.
- **Goals:** record a daily maximum for one medication, with a start date, optional end date, and optional note. Future goals are supported.
- **Past days:** summaries of days with recorded intakes, newest first, with 20 days shown initially and a **Load more** button. Open any day for its entries, totals, and recorded goals, or add a missed intake.
- **Card stacks:** Today and past-day detail cards have an 8px gap, a coordinated one-time entrance as they become visible, and an occasional glass shine across exposed cards. Equal taken times keep their source order. Invalid legacy taken times remain separate at the end of the grouped output. Each intake retains its entered quantity, time, creation timestamp, and note; dose follows its medication’s current strength. Folded rear cards show roughly their bottom quarter, capped at 26px for long notes. Every rear card has the same 2% inset on each side, without progressive staggering; expanding reveals each complete card at that uniform 96% width. All rear cards also use the same 10px vertical padding, keeping ordinary rear cards at 76px while the front remains 80px; text and icon sizes stay unchanged. Tap anywhere on a collapsed stack to reveal its entries; only a subsequent card activation opens its editor. The compact footer can collapse it again, with both disclosure states updating immediately. Keyboard disclosure moves focus to the first revealed entry. Measured card heights keep long notes and resized layouts fully visible. Disclosure and editing remain immediate; the shared page entrance stays disabled on Today and past-day detail routes so it does not double the card motion. There are no intake-card hover animations.
- **Streak Milestones:** open Streaks from the header navigation for only the latest three unlocked milestones and the next three new targets. Achievements follow the best recorded consecutive-day run and stay unlocked after a gap; current-run progress is shown separately. Earned cards, detail heroes, and the active streak popover use coordinated colorful glass, glowing gradients, waves, orbit outlines, sparkles, and confetti. First-earned dates and comparisons are derived from current records, so edits and backfills can update them. Details compare equal calendar windows: the first stretch that earned the milestone and the immediately preceding period. Energy and stress changes use self-reported check-in averages with at least two ratings in each window; sleep hours stay a neutral change. Medication totals and averages remain separate, use only days with a record for that medication, and are never judged as better or worse. Missing records remain unknown. Coverage, recorded-day links, moods, and short reflection excerpts provide context without inventing a result.
- **Corrections:** tap a single or expanded intake card to edit its medication, quantity, time, or note. The card shows time and medication name above the active ingredient and quantity × strength, with a compact rose Benzo marker beside that lower row when applicable. Delete an intake through an explicit confirmation.
- **Preferences and backups:** change the journal timezone, sign out, or download a JSON export from the history page.

## Tracking days, quantities, and goals

### Logging streaks and milestones

The counter beside the date always uses the filled-stars icon, matching the top-right streak button and the theme’s primary text color. It counts consecutive tracking days with at least one saved intake. If today has no intake yet, an uninterrupted run ending yesterday remains current; an older gap ends that run. A small secondary label describes that count as **3 days / in a row**. The streak details popup retains days remaining until the next consecutive-day milestone. The milestones are **2, 3, 4, 5, 7, 10, 13, 15, 17, 20, 25, 30**, followed by **35, 40, 45**, and further five-day increments without a cap. Reaching a milestone advances the next target immediately. Backdated, edited, and deleted entries update the counter and remaining days immediately.

The top-right stars button opens a popover with the current streak, days to the next milestone in this run, best streak, and total days with entries. An active run gets a vivid celebration with the shared milestone artwork, emoji medallion, progress track, and a link to Streaks; zero current days use a quieter neutral surface. Its compact close target remains 32px with a 28px face and 14px icon. It updates from the same live journal and tracking-day calculation as the date counter, and closes through outside click, Escape, its explicit close button, navigation, or route changes. Focus returns to its trigger on dismissal. Achievements in the list follow the lifetime best run, while this popup always shows current-run progress.

These counts describe saved records, not dose-goal compliance or proof that every intake was logged. Multiple entries on a day count once, regardless of dose. The journal timezone and 06:00 boundary apply, including daylight-saving changes. Invalid or future timestamps do not contribute.

Each home-page request selects one of six playful streak icons on the server. The icon stays stable during the visit to avoid flickering or hydration mismatches. The former separate badge, progress bar, and encouragement section are removed; the retained server-only encouragement bank is not selected or sent to the home page.

### A new day begins at 06:00

The default journal timezone is **Europe/Vienna**. An intake taken at 05:59 belongs to the previous tracking day; one taken at 06:00 belongs to the new day. The home page switches days automatically while open. Previous entries stay saved in history.

Times are stored as UTC timestamps and interpreted using the journal's IANA timezone, independently of the device timezone. The day calculation uses the local calendar, so daylight-saving days can contain 23 or 25 hours. Changing the timezone regroups existing entries without changing their timestamps.

The date/time field opens at the current time for a new log. When adding a missed intake from a past day's page, it starts at noon on that day. The form shows which tracking day will receive the entry. Future intake times are rejected. A nonexistent local time during the spring clock change is rejected; a manually entered repeated time during the autumn clock change selects its earlier occurrence. An unchanged time field preserves the original instant and seconds, including entries from the second occurrence of a repeated hour.

The timeline is ordered by **Date & Time Taken**, from earliest to latest. Backdated entries appear at their recorded time and join the appropriate rolling 13-minute group, extending or bridging stacks when the consecutive gaps allow it. Creation timestamps remain saved but do not determine the displayed order.

### Each medication stays separate

Enter strength in **mg per tablet, capsule, drop, or other unit**, using the medication packaging. The amount field records a quantity of those units, including decimals. The calculated dose is:

```text
current strength in mg per unit × logged quantity = dose in mg
```

The app does not convert between medications or add different medications into one combined dose. A daily goal and its progress always belong to one medication.

Medication edits apply to every linked intake, including older records created before this policy. Names, strengths, and medication types follow the current medication; changing strength recalculates each dose and every daily total from its actual logged quantity. Quantity, intake time, creation time, notes, and chosen goal limits remain unchanged. Default-quantity changes only affect new-log prefills. The optional `isBenzodiazepine` boolean is separate medication metadata: legacy absence is unmarked, explicit false clears a previous mark, and unrelated edits or archiving preserve it. APIs accept only true/false values for that field. Exports include it with medication details; no intake classification snapshot or storage migration is needed. State and backup reads reconcile old details immediately without writing to storage. Each successful mutation persists the reconciled history within the same atomic save, including concurrent-save retries; failed saves cannot partially update medication details or history. Entries without a linked medication retain their saved name, strength, and unit as a readable fallback. The intake editor also uses the current medication details, even when an open editor outlives an update in another window.

### Goals are personal reference values

Goals are nonnegative daily maximums entered by the user, rather than a generated taper plan. When several goals apply to the same medication and day, the one with the latest start date applies; if start dates match, the most recently created goal applies. Start and end dates are inclusive. A newer goal permanently supersedes earlier goals from its start date. When that newer goal expires, no maximum applies until another goal starts; older maximums do not silently return.

Create a new goal to change a target over time. Removing a goal also removes its effect on historical summaries; intake records remain saved. Progress describes the entries recorded so far and does not prescribe a dose.

Work with your prescriber on dose changes. Stopping benzodiazepines suddenly or reducing them too quickly can cause dangerous withdrawal, including seizures; tapering needs an individual plan and support. See the [FDA's benzodiazepine safety guidance](https://www.fda.gov/drugs/drug-safety-and-availability/fda-requiring-boxed-warning-updated-improve-safe-use-benzodiazepine-drug-class).

3. Generate credentials on your own machine:

   ```sh
   npm run secrets
   ```

   The script prints a random `APP_PASSWORD` and `SESSION_SECRET` in the terminal. Save the password in your password manager and copy both values into the project's private Vercel environment variables.

4. Ensure the three required production variables are configured, then deploy or redeploy so the running app receives them.
5. Open the deployment, sign in, add a medication from its packaging, and save a test entry. Reload to confirm persistence, then delete that test entry.

The tracked `vercel.json` selects the Next.js preset and pins functions to Frankfurt (`fra1`), matching the initial Neon database region.

The server creates its tables automatically on first database use. The database connection therefore needs permission to create tables. The password-journal update adds credential and registry tables and preserves the original `personal` journal row, including its version and timestamp. The repeatable schema statements live in `src/lib/server/journal-repository.ts`; no manual data migration is needed.

For Preview deployments, configure the same authentication requirements with a separate Neon database or branch. This keeps preview changes separate from the personal production journal.

### Environment reference

| Variable         | Purpose                                                                                                                                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`   | Neon Postgres connection string. Required in production. The Marketplace integration normally supplies it.                                                                                                 |
| `APP_PASSWORD`   | Password for the original personal journal, at least 4 characters. Required in production or when a database or password is configured. Additional journal passwords are created through the login screen. |
| `SESSION_SECRET` | Random session-signing secret, at least 32 characters. Required alongside authentication.                                                                                                                  |

Production fails closed until the database, password, and session secret are configured. It never falls back to local file storage in production. The login page displays generic setup guidance when configuration is incomplete.

Changing `APP_PASSWORD` changes access to the original personal journal and invalidates its sessions. Changing `SESSION_SECRET` invalidates all sessions; additional journals keep their passwords because password verifiers do not depend on the signing secret. Sessions last up to 400 days and use persistent HTTP-only cookies, marked secure in production, with `SameSite=Lax`, `Priority=High`, and path `/`. Lax allows a valid session on incoming top-level navigation, where Strict could show the sign-in page despite a stored cookie. Every verified state load or cookie-only session check reapplies the current cookie policy; the signed token renews at most daily. Existing valid 30-day sessions upgrade automatically; expired, tampered, or revoked tokens are never renewed. The 400-day setting follows [Chrome’s persistent-cookie limit and renewal behavior](https://developer.chrome.com/blog/cookie-max-age-expires).

The journal checks again when its window becomes visible, returns from the back/forward cache, regains focus, or comes online. Concurrent refreshes share a request, and a 20-second deadline prevents a stalled mobile load from blocking later attempts. Visible, continuously open windows also make a lightweight check every six hours. That endpoint returns only authentication status and never loads journal records. A transient 401 gets a short session-recovery window before redirecting; unavailable servers, timeouts, and contradictory authentication responses keep the current screen with a retry message. A restored session retries only the journal GET, never a medication or intake save. The sign-in screen can recover a delayed saved cookie before the user starts typing. Successful sign-in and sign-out use a fresh document navigation to avoid stale authentication responses in the router cache.

Normal reloads, closing and reopening the browser or PWA, and device restarts should preserve the persistent cookie when the browser retains its site data. Browsers or operating systems may clear it earlier; clearing site data, explicit sign-out, and credential revocation require signing in again. Safari and its installed Home Screen app can have separate cookie stores, so sign in inside the installed app if needed. The password and bearer token are never copied into local storage, IndexedDB, or service-worker caches. Sign out through **Past days → Preferences**; this cancels the window’s background checks and clears its cookie even if that session has already expired. Same-origin validation remains required for sign-out and all other mutations.

## Storage and privacy

Each exact password selects one journal. There are no usernames, email addresses, or password-reset flow. Passwords preserve spaces, case, and Unicode without normalization and accept 4–1,024 characters using the input's native length rules. The creation confirmation displays the password in plain text only while it is open. Cancelling creates nothing; an existing password opens its journal directly. Duplicate creation, including simultaneous requests, cannot replace a journal's records.

Authentication protects the application routes and API. Every data read, mutation, and export derives its journal from the verified session cookie; request parameters cannot select another journal. Existing original-journal sessions remain compatible. Mutations require the same origin, inputs are validated on the server, and sign-in is limited to 10 attempts per 15-minute window across the installation. Creation also has a separate 10-attempt window. Successful sign-in or creation does not reset either counter, so access to one journal cannot bypass the limit for another. Database-backed rate limiting works across Vercel function instances.

Additional journal passwords use scrypt with a random 16-byte salt, a 64-byte verifier, and constant-time verification. Plain-text passwords are not stored in the credential tables, session cookies, URLs, or browser storage. Password lookup verifies the stored salted hashes rather than maintaining a fast password index. This design is intended for personal use and caps additional journals at 50; lookup time grows with the number of journals.

The production database has four tables:

| Table                           | Contents                                                                                                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pill_happens_state`            | One document per journal containing medications, linked intake details, goals, and timezone settings, plus its version counter and update timestamp. |
| `pill_happens_login_attempts`   | Separate installation-wide sign-in and creation counters and rate-limit windows.                                                                     |
| `pill_happens_journal_registry` | A version counter used to serialize concurrent credential creation.                                                                                  |
| `pill_happens_journals`         | Additional journal identifiers, salted scrypt password verifiers, and creation timestamps.                                                           |

Updates use optimistic version checks and retry on contention to avoid overwriting a simultaneous save. The client also prevents overlapping saves within one open app instance. The full journal is loaded into the client; the 20-day history limit controls the display, rather than database pagination. This is intentionally sized for personal use.

There is no runtime analytics or advertising integration. Journal responses use `private, no-store`; database details and submitted notes are not written to application error logs. The app does not implement client-side or field-level encryption. Access to the hosting and database accounts also grants access to stored records.

`.env` files, local data, Vercel project metadata, and build artifacts are ignored by Git. Keep actual intake records and credentials out of commits, screenshots, and issue descriptions.

## Export and backups

Use **Past days → Export journal** while signed in. The authenticated `/api/export` endpoint downloads a JSON document containing:

- `schemaVersion` and `exportedAt` metadata;
- all medications, including archived items;
- all intake records with current medication details, timestamps, quantities, and notes;
- all goals and notes;
- the journal timezone.

Exports contain personal records and should be stored privately. The prototype has **no import or restore interface**. An export can be inspected or used for a future migration; database recovery should use the database provider's backup tools. Local development data is a separate dataset and is not automatically migrated when a production database is connected.
